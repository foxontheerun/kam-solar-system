## Units and constants

The simulator works in dimensionless code units chosen so that:

- `G = 1` — gravitational constant
- `M_sun = 1` — mass of the Sun
- `a_earth = 1 AU` — Earth's semi-major axis

This gives a natural unit of time set by Kepler's third law applied to Earth. For a Keplerian orbit:

```
T² = (4π² / GM) · a³
```

For Earth with `a = 1`, `GM = 1`:

```
T_earth = 2π
```

So **one year equals 2π units of code time**, and the conversion in `animation-loop.js` is:

```js
const years = this.physics.totalTime / (2 * Math.PI);
```

Planet masses in `data.js` are stored as fractions of `M_sun`. These are the real mass ratios:

- Jupiter: `9.54e-4` (≈ 1/1047)
- Saturn:  `2.86e-4` (≈ 1/3499)
- Earth:   `3.00e-6`
- Mercury: `1.66e-7`

## Initial conditions

Each planet is placed at **perihelion** (the orbital point closest to the Sun) at t = 0. Given orbital elements (`a`, `e`, `i`, `Ω`, `ω`):

**Radial distance at perihelion:**

```
r_peri = a · (1 − e)
```

**Speed at perihelion** from the vis-viva equation `v² = GM · (2/r − 1/a)`. Substituting `r = a(1 − e)`:

```
v_peri = sqrt(GM · (1 + e) / (a · (1 − e)))
```

These scalars are rotated from the orbital frame into 3D space using the three orbital angles. The ecliptic is taken as the XZ plane and Y as the out-of-plane axis. Following Murray & Dermott (1999):

```
x = r · (cos θ · cos Ω − sin θ · cos i · sin Ω)
y = r · (sin θ · sin i)
z = r · (cos θ · sin Ω + sin θ · cos i · cos Ω)
```

where `θ` is the angular position in the orbital plane (true anomaly plus argument of perihelion). The velocity vector is generated by the same transformation with `θ → θ + π/2`, exploiting the fact that velocity is perpendicular to the radius vector at perihelion.

See `src/orbital-mechanics.js::placePlanetState`.

## N-body integration: Velocity-Verlet

The integrator is **Velocity-Verlet**, also known as the kick-drift-kick form of symplectic leapfrog:

```
v(t + dt/2) = v(t)         + (dt/2) · a(t)
x(t + dt)   = x(t)         + dt    · v(t + dt/2)
a(t + dt)   = compute_accelerations(x(t + dt))
v(t + dt)   = v(t + dt/2)  + (dt/2) · a(t + dt)
```

Two acceleration evaluations per step, ping-ponged between pre-allocated buffers to avoid allocations in the hot path.

### Why Velocity-Verlet?

- **Euler** (1st order, not symplectic): energy drifts secularly — Earth's orbit would spiral outward over long integrations. Unacceptable for orbital dynamics.
- **RK4** (4th order, not symplectic): much smaller per-step error but still drifts energy slowly. Better than Euler but still wrong for long-term celestial mechanics.
- **Velocity-Verlet** (2nd order, **symplectic**): exactly preserves a "modified" Hamiltonian H̃ that differs from the true H by O(dt²). Energy and angular momentum oscillate around true values rather than drifting away. This is the right family of integrators for problems where orbits must stay closed over many periods.

Step size `SIM_DT = 0.005` code-time units. In years: `0.005 / (2π) ≈ 0.0008` year ≈ 7 hours. Tight enough to resolve Mercury (the innermost, fastest body, perihelion velocity ~60 km/s) with hundreds of steps per orbit.

See `src/physics-engine.js::step` and `_computeAccelerations`.

## Forces

### Newtonian gravity (pairwise)

For each ordered pair `(i, j)` with `i < j`:

```
d   = x_j − x_i
r²  = |d|²
inv = 1 / (r² · sqrt(r²))      // 1 / r³

a_i += G · m_j · d · inv        // Newton's third law
a_j −= G · m_i · d · inv        //   handled symmetrically
```

With N = 9 bodies the inner loop runs `C(9, 2) = 36` pair interactions per acceleration evaluation. Trivially fast.

### Drag (linear, gas-disc analog)

When the drag slider is non-zero, each body except the Sun receives an additional acceleration:

```
a_drag = −k · v
```

This is the simplest possible dissipative term — bulk gas drag in a protoplanetary disc. The orbital evolution is derived as follows.

Power dissipated per unit mass:

```
dE/dt = a_drag · v = −k · v²
```

For a circular orbit, `v² = GM/a` and the specific orbital energy is `E = −GM/(2a)`. So:

```
dE/dt = −k · GM / a
dE/da = GM / (2a²)
da/dt = (dE/dt) / (dE/da) = −2k · a
```

Solution:

```
a(t) = a₀ · exp(−2kt)
```

E-folding time `τ = 1 / (2k)` in code units, equivalently `τ_years = 1 / (4πk)`.

For `k = 5.4 · 10⁻³` (slider value ≈ 91 of 100), `τ ≈ 15 years`. Earth crosses the capture radius `0.18 AU` at:

```
t = (1 / 2k) · ln(a₀ / r_capture) ≈ 26 years
```

A counter-intuitive consequence: drag **decelerates** the planet locally but the planet's average orbital speed **increases** as it spirals inward, because lower orbits are faster. This is the same effect that requires retrograde burns to descend in spacecraft orbital mechanics.

**Caveat on symplecticity.** Velocity-Verlet is symplectic only when the acceleration is purely position-dependent. With drag added, `a = a_grav(x) + a_drag(v)` — the integrator drops from 2nd-order symplectic to a 1st-order non-symplectic operator splitting. The closed-form `a(t) = a₀ · exp(−2kt)` derived above is the analytic result for the true ODE; the numerical integration approximates it well over the simulation horizon but is not exact. A Strang-split scheme (half drag-kick → full conservative Verlet step → half drag-kick) would restore 2nd-order accuracy on the dissipative part and is the standard fix; it's not implemented here because the demo prioritises clarity and visual fidelity over long-time quantitative claims under drag.

See `src/physics-engine.js::_computeAccelerations`.

## Coordinate frames

The simulation supports two visual frames:

1. **Heliocentric** (default): Sun fixed at origin. Each planet's screen position is `x_planet − x_sun`. This is what we're used to seeing in textbook diagrams.

2. **Inertial**: the **barycenter** (centre of mass of the whole system) is fixed at origin. The Sun visibly wobbles. In reality, the barycenter of the Sun–Jupiter pair lies `1.07 R_sun` outside the Sun's surface, which is the basis of the radial-velocity exoplanet-detection method.

The physics integration is always carried out in the inertial frame internally. The heliocentric view is purely a display transformation.

At initialisation, `recenterCOM()` subtracts the centre-of-mass position and velocity from every body, so the total linear momentum is zero and the system stays anchored at the scene origin:

```
x_COM = Σᵢ mᵢ · xᵢ / Σᵢ mᵢ
v_COM = Σᵢ mᵢ · vᵢ / Σᵢ mᵢ
xᵢ ← xᵢ − x_COM
vᵢ ← vᵢ − v_COM
```

The trails are sampled in either frame depending on the current selection — switching frames clears trail buffers to avoid a discontinuous jump.

See `src/physics-engine.js::recenterCOM` and `src/animation-loop.js::_sampleTrails`.

## Derived quantities

### Instantaneous eccentricity (Laplace–Runge–Lenz vector)

For the pure two-body problem, the Laplace–Runge–Lenz (LRL) vector is conserved exactly:

```
e_vec = (v × h) / μ − r̂
```

where:

- `h = r × v` is specific angular momentum
- `μ = G · M_sun` is the gravitational parameter (test-particle approximation, matching `placePlanetState`)
- `r̂ = r / |r|` is the unit radius vector

`|e_vec|` equals the orbital eccentricity. In the full N-body simulation this is *not* exactly conserved — it oscillates and drifts under perturbations from the other planets. That oscillation is itself the interesting quantity, and it's what the HUD shows as "Mercury e_max" / "Earth e_max" / "Mars e_max" — the largest eccentricity observed during the current run.

Capped at 2 in code to keep ejected planets from blowing up the numeric display.

See `src/orbital-mechanics.js::instantaneousEcc`.

### Orbital period (Kepler's third law)

The legend shows each planet's current Keplerian period. From `T² = 4π² · a³ / (GM)` with `GM = 1`:

```
T_code = 2π · a^(3/2)
T_years = T_code / (2π) = a^(3/2)
```

In code units where Earth has `a = 1` and `T = 1` year, the formula reduces to `T = a^(3/2)` evaluated directly in years. When a KAM preset moves Jupiter to `a = φ^(2/3) ≈ 1.376 AU`, the legend updates to show `T ≈ 1.62 years`.

This is the *nominal* Keplerian period assuming an unperturbed two-body Sun–planet system. It does not account for slow modulation by other planets' gravity, nor for drag-driven inward migration. For the latter, the relevant timescale is the e-folding time of the drag decay, not the orbital period.

See `src/ui-controller.js::_renderLegend`.

## Sun capture

When a planet's distance from the Sun's centre falls below `SUN_CAPTURE_RADIUS = 0.18 AU`, the planet is marked as consumed: its mesh, orbit line, and trail are hidden, and it is excluded from subsequent force calculations. The label is added to the HUD's "consumed by Sun" list.

The threshold of `0.18 AU` is well below Mercury's perihelion distance (`a · (1 − e) = 0.387 · 0.794 = 0.307 AU`), leaving a comfortable `0.127 AU` margin so natural eccentricity oscillations cannot trigger spurious captures. It is also small enough that any genuine inward spiral under drag or resonance kicks reliably crosses the threshold before the planet would visibly penetrate the Sun's mesh.

See `src/physics-engine.js::checkCaptures`.

## KAM presets and their physical meaning

The KAM-stability panel implements four scientifically meaningful configurations plus a reset.

### Real (5.20 AU)

Jupiter at its actual semi-major axis. The system runs in its real configuration. The other slider perturbations (mass scale, eccentricity scale, inclination scale, drag) all return to zero. This is the calibration state.

### φ — stable

Jupiter placed at `a = φ^(2/3) ≈ 1.376 AU`, where φ = (1 + √5) / 2 is the golden ratio. By Kepler's third law, this makes the Jupiter:Earth period ratio exactly equal to φ.

The Kolmogorov-Arnold-Moser theorem states that quasi-periodic orbits in nearly-integrable Hamiltonian systems survive small perturbations *provided their frequency ratio is sufficiently irrational* — specifically, poorly approximated by rational numbers. The continued-fraction expansion of φ is `[1; 1, 1, 1, ...]`, which is the slowest-converging of any irrational; in the sense of Hurwitz's theorem, φ saturates the Markov constant `1/√5`, so it is in this technical sense "the most irrational number". Orbits at golden-ratio frequency ratios occupy the largest measure of surviving tori as the perturbation grows.

In this preset no mass scaling is applied. KAM theorems do **not** strictly guarantee infinite stability at Jupiter's realistic mass ratio (`9.5 · 10⁻⁴ M_sun`) — the rigorous Diophantine bound applies to much smaller perturbations than this. What we get in practice is that no instability develops within the simulation horizon, so the orbits *appear* locked indefinitely on visible timescales. This is consistent with numerical experiments (Wisdom 1980, Holman & Wisdom 1993) showing that φ-ratio orbits at these mass ratios are dramatically more stable than nearby integer-ratio configurations, even when neither is rigorously KAM-protected.

### 2:1 → collapse

Jupiter at `a = 2^(2/3) ≈ 1.587 AU`. The Jupiter:Earth period ratio is exactly 2:1 — a strong **mean-motion resonance**.

At a 2:1 resonance, every two Earth orbits coincide with one Jupiter orbit; the relative geometry between the planets repeats periodically, and gravitational perturbations from Jupiter add coherently instead of averaging out. With Jupiter's mass scaled `× 50` in this preset, the inner planets get kicked into chaotic orbits within decades.

This is the same mean-motion resonance mechanism that, **at a different scale**, carves the **Kirkwood gaps** in the real asteroid belt. There, Jupiter sits at its actual 5.2 AU and the 2:1 resonance falls on asteroids at `a = 3.27 AU` — those have been long since cleared. In our preset Jupiter has been moved inward and Earth plays the role of the test particle at the 2:1 ratio; the physics is identical, only the bodies and distances differ.

### 3:1 → collapse

Jupiter at `a = 3^(2/3) ≈ 2.08 AU`. Jupiter:Earth period ratio 3:1. Same MMR mechanism as the 2:1 preset, slightly weaker coupling — hence mass scaling `× 30` instead of `× 50` to produce comparable collapse. The real-Solar-System analog is the Kirkwood gap at `a = 2.50 AU` (asteroids in 3:1 with Jupiter at 5.2 AU).

### ⚠ break KAM

Jupiter at the 2:1 resonance position (`a = 2^(2/3) AU`) with planet masses scaled `× 800`. Jupiter's gravitational mass becomes `9.54 · 10⁻⁴ · 800 = 0.76 M_sun` — comfortably above the hydrogen-burning threshold at `~0.08 M_sun`. **Gravitationally** Jupiter is now of stellar mass; the simulator only changes its gravitational `m`, not its physical structure, radius, or luminosity. A real 0.76 M_sun object would be a K-dwarf main-sequence star, but here it stays the same visual sphere — we're studying the dynamical consequences of the mass change, not pretending to model stellar physics.

With Jupiter at stellar mass, the Sun–Jupiter pair forms a tight binary. Inner planets fall inside Jupiter's enlarged Hill sphere (`R_Hill ≈ 1.0 AU` at × 800 mass) and are absorbed by the Sun or by Jupiter within their first orbital period — at this preset the collapse is mass-dominated rather than resonance-dominated. Neptune (originally at 30 AU) is left far enough out that it survives, and ends up on a **circumbinary** orbit — an orbit around the centre of mass of the Sun–Jupiter binary — tracing the characteristic epicyclic loops first studied by Euler in the 18th century and now observed in real exoplanet systems like Kepler-16b (Doyle et al. 2011).

## The asteroid belt is decorative

The 1500 particles between Mars and Jupiter are *not* part of the N-body system. They follow independent circular Kepler orbits with semi-major axes uniformly distributed in `[2.2, 3.2] AU` and small out-of-plane offsets. Each particle stores its own (a, phase, mean motion, y-offset) and is moved every frame by direct kinematic update from the simulation time:

```js
angle_i = phase_i + n_i · time
x_i     = a_i · cos(angle_i)
z_i     = a_i · sin(angle_i)
```

where `n_i = a_i^(−3/2)` is the mean motion (Kepler's third law).

The particles do not feel the planets, do not feel each other, and the Sun's gravity is implicit only via the choice of `n_i ∝ a^(−3/2)`. The belt is parented to the Sun's three.js group, which means it rigidly tracks the Sun's position; in the inertial frame it wobbles with the Sun rather than orbiting the barycenter as a real asteroid belt would. This is a known simplification.

The belt is auto-hidden when the system collapses (a planet falls into the Sun), so that the visual contradiction of asteroids peacefully orbiting through a destroyed inner system doesn't mislead the viewer.

See `src/asteroid-belt.js`.

## What is NOT modelled

- **General Relativity.** The relativistic contribution of `43"/century` to Mercury's perihelion precession — the part Einstein famously explained — is absent. The simulator is *expected* to reproduce the classical `~532"/century` from planetary perturbations alone, but this is a secular result requiring long-time integration and careful fitting; the demo doesn't actually measure or validate the precession rate. The often-quoted total of `~5600"/century` further includes the precession of the vernal equinox, which is a choice-of-frame artefact.
- **Solar oblateness (J2 moment).** The Sun is mildly rotationally flattened, contributing a small extra precession term to inner-planet orbits. Neglected.
- **Tidal effects.** No body raises tides on another. Tidal dissipation drives long-term evolution (Moon receding from Earth, Mercury's 3:2 spin-orbit lock) but is irrelevant on the timescales shown here.
- **Radiation pressure and solar wind.** Real dust feels both. The asteroid-belt particles here have no mass and don't participate in force calculations, so the question doesn't arise.
- **Solar mass loss.** The Sun is losing roughly `10⁻¹⁴ M_sun/year` to wind. Negligible on 1000-year timescales.
- **Stellar perturbations.** No passing stars, no Oort-cloud objects, no galactic tide. The system is closed.
- **Three-body mean-motion resonances.** Jupiter's moons exhibit the famous Laplace 4:2:1 Io–Europa–Ganymede resonance, and the Solar System contains other multi-body resonances. None of those are reproduced — the simulation has no moons or minor bodies that interact gravitationally.
- **Yarkovsky / YORP forces.** Thermal-emission asymmetries that slowly modify asteroid orbits. Asteroid belt is decorative, so irrelevant.

## References

- Murray, C. D. & Dermott, S. F. (1999). *Solar System Dynamics*. Cambridge University Press. The definitive textbook on planetary celestial mechanics; the orbital-element transformations and vis-viva derivation in this code follow its conventions.
- Wisdom, J. & Holman, M. (1991). "Symplectic maps for the N-body problem". *Astronomical Journal* 102: 1528. Foundational paper on symplectic integrators for long-term planetary simulations; motivates the use of Velocity-Verlet over RK4 here.
- Laskar, J. (1989). "A numerical experiment on the chaotic behaviour of the Solar System". *Nature* 338: 237. Showed that the inner Solar System is chaotic on Gyr timescales, with Mercury–Mars in particular exhibiting Lyapunov exponents of `~1 / 5 Myr`.
- Kolmogorov, A. N. (1954) → Arnold, V. I. (1963) → Moser, J. (1962). The three foundational papers of KAM theory. Arnold's *Russian Math. Surveys* 18: 9 (1963) is the most accessible English starting point.
- Doyle, L. R. et al. (2011). "Kepler-16: A transiting circumbinary planet". *Science* 333: 1602. Discovery of the first transiting circumbinary planet, the real-world analog of the «break KAM» preset configuration.
- Wisdom, J. (1980). "The resonance overlap criterion and the onset of stochastic behavior in the restricted three-body problem". *Astronomical Journal* 85: 1122. The mechanism behind the Kirkwood gaps and behind the 2:1 / 3:1 catastrophic-collapse presets here.
